# Base64 codec 기능 리뷰

- 검토일: 2026-08-30
- 검토 표면: `worktree/lucky-cloud-860c`의 현재 작업 트리(커밋 `6025eb0` 및 미커밋 UI 변경 포함)
- 공개 상태: `base64-decode`, `base64-encode` 모두 현재 `tool-registry.js`에서 `indexable`
- 결론: 오류 복구를 숨기지 않는 점, 바이너리 결과 취급, 큰 입력의 Worker 처리와 최신 요청 우선 제어가 강점이다. 반면 반복 디코드가 기본값인 점은 원문을 한 단계 이상 바꿀 수 있으므로 가장 먼저 재검토해야 한다. 경쟁 서비스보다 지원 표준과 문자셋 폭은 좁다.

## 소유 경계와 근거

- 경로: `/{locale}/base64-decode/`, `/{locale}/base64-encode/`
- 화면/상태: `apps/web/src/features/base64/{Base64Page.astro,Converter.astro,client.ts,worker.ts,contract.ts,mode-definition.ts,run-preparation.ts}`

- 브라우저 QA: `scripts/qa/base64_feature.py`
- 공개·현지화 근거: `apps/web/src/lib/tool-registry.js`, `apps/web/src/lib/locale-review-manifests/base64-codec.json`

## 이미 개선된 점

1. 표준 Base64와 Base64URL을 자동 감지하거나 명시적으로 선택할 수 있고, 패딩·공백·data URI 제거와 선택적 유연 복구를 구분한다. 적용한 복구는 `RepairCode` 배지로 사용자에게 드러낸다.
2. UTF-8뿐 아니라 EUC-KR/CP949, Shift-JIS, GB18030, Big5, Windows-1252를 UI에서 고를 수 있다. 텍스트/hex 보기도 분리한다.
3. 텍스트와 파일을 모두 처리하며, 파일 인코드는 원시 바이트를 Worker로 전송한다. 100 MiB 상한, 1 MiB 이하 자동 실행, 그보다 큰 입력의 명시 실행 정책이 코드에 고정돼 있다.
4. PNG/JPEG/GIF/WebP/PDF/ZIP/PE 매직 바이트를 확인해 확장자와 취급 방식을 결정한다. 이미지로 확인된 결과만 미리 보고, 실행 파일은 경고한다. data URI에 적힌 MIME만 신뢰하지 않는 테스트도 있다.
5. 최신 요청만 결과 권한을 가지도록 `LatestWorkerRunner`를 쓰고, 취소된 Worker·파일 읽기·클립보드 완료가 새 입력을 덮지 못하게 한다. `dd82282`에서 Base64 Worker 실행을 공통 최신요청 모델로 통합했다.
6. `02a7c57`에서 최대 10단계 반복 디코드와 중단 규칙을 추가했다. 다음 층이 알려진 파일이거나 텍스트로 보기 어려우면 더 깊게 해석하지 않고, 실제 반복 횟수를 배지로 표시한다.
7. 현재 미커밋 표면은 공통 `ToolModeSwitch`와 헤더 문맥 라벨을 적용하고, 반복 디코드 옵션을 화면에 노출한다. 이 항목은 아직 커밋된 제품 이력으로 보아서는 안 된다.

## 경쟁 페이지 관찰

관찰일은 모두 2026-08-30이며, 아래 내용은 해당 페이지에 직접 노출된 기능만 기록했다.

| 경쟁 페이지 | 직접 관찰한 기능 | 현재 제품과의 관계 |
| --- | --- | --- |
| [Base64.Guru Base64 Decode](https://base64.guru/converter/decode) | 표준 자동 감지, strict 모드, 문자 인코딩 선택, 복사/다운로드, Main·MIME·ASCII Armor·Base64URL·IMAP·PEM·XML 이름 계열 표준 | 표준/문자셋 폭은 경쟁 페이지가 강하다. 현재 제품의 복구 내역 배지, 매직 바이트 기반 바이너리 경고, 이미지 미리보기, 반복 디코드는 이 페이지에서 같은 형태로 관찰되지 않았다. |
| [Base64.Guru Base64URL Encode](https://base64.guru/standards/base64url/encode) | 텍스트·로컬 파일·원격 URL을 입력으로 받아 Base64URL 생성 | 로컬 텍스트/파일은 대체로 동등하다. 원격 URL 입력은 현재 제품에 없다. 현재 제품은 표준/Base64URL, MIME 줄바꿈, data URI를 한 화면의 옵션으로 묶는다. |

### 상대 평가

- 더 강한 부분: 복구가 일어났는지 구체적으로 표시하는 설명 가능성, Worker 취소와 stale-result 방지, 원시 파일 바이트 전송, 바이너리/실행 파일 경고, 생성한 이미지의 로컬 미리보기.
- 대체로 동등한 부분: 일반 Base64·Base64URL 텍스트 변환, strict 선택, 문자셋 선택, 파일 입력, 복사·다운로드.
- 약한 부분: Base64.Guru가 노출한 MIME/ASCII Armor/IMAP/PEM/XML 계열 표준과 훨씬 넓은 문자셋, 원격 URL 입력. 성능 우위는 같은 파일·브라우저·측정 절차가 없으므로 판단하지 않았다.

## 안전한 claim 후보

- “표준 Base64와 Base64URL을 인코드·디코드하고, 자동 복구가 적용되면 그 항목을 표시합니다.”
- “현재 구현은 도구 입력과 파일 바이트를 브라우저 메모리와 Web Worker에서 처리하며 변환 API로 보내지 않습니다.”
- “PNG, JPEG, GIF, WebP 등 일부 알려진 파일 서명을 감지하고, 실행 파일로 보이는 결과에는 경고를 표시합니다.”
- “UTF-8 텍스트와 로컬 파일을 지원하며, 최대 입력 크기는 현재 UI 정책상 100 MiB입니다.”

## 금지하거나 조건부로만 쓸 claim

- “가장 빠른/가장 안전한/가장 많은 형식을 지원하는 Base64 도구”: 동등 조건 벤치마크와 전체 시장 조사가 없다.
- “모든 바이너리 형식을 정확히 식별”: 매직 바이트 목록은 제한적이며 MIME 판별기가 아니다.
- “악성 파일 탐지”: PE 서명 경고일 뿐 악성 여부를 판정하지 않는다.
- “모든 데이터가 절대 네트워크로 나가지 않는다”: 도구 데이터는 로컬이지만 페이지 자체의 폰트·분석·광고 요청 여부와 구분해야 한다.
- “손상된 Base64를 항상 올바르게 복구”: 유연 복구는 문자를 제거할 수 있어 원래 의도를 보장하지 않는다.
- “Base64는 암호화”: 인코딩일 뿐 기밀성을 제공하지 않는다.

## 검증과 한계

- 현재 root 표면의 소스·미커밋 diff, `02a7c57`, `dd82282`, `f4f6efb` 이력을 확인했다.
- 관련 Vitest 17개(`codec-core` 13개, run preparation 4개)가 2026-08-30에 통과했다. 전체 묶음 결과는 6파일 41테스트 통과였다.
- 기존 QA가 다국어 UTF-8 왕복, mode URL/metadata, 빠른 입력 중 빈 결과 방지, 파일/옵션/모바일 표면을 검사하는 것을 확인했다.
- 경쟁 페이지는 공개 HTML에서 관찰했으며 로그인 뒤 기능·서버 내부 처리·실제 성능은 검증하지 않았다.
- 인앱 브라우저 연결 제약으로 현재 미커밋 표면을 별도 수동 브라우저 세션에서 재실행하지 못했다. 따라서 미커밋 mode switch와 반복 옵션은 소스/QA 계약 근거이며 배포 완료 claim이 아니다.
